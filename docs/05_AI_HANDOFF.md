# Restaurant App — AI Handoff Protocol

## Purpose

Operational safety protocol for Claude, Codex, ChatGPT, or another coding assistant.

This file does not authorize work. Always read `03_CURRENT_WORK.md` before modifying production code.

## Token-Efficient Agent Workflow

The repository is the source of truth. Avoid repeating project history, accepted decisions, or long test checklists in every prompt when they are already documented.

### Role split

Claude and Codex may both act as developers. Roles are assigned **per authorized slice**, not permanently by agent identity. The authoritative current assignment lives in `docs/03_CURRENT_WORK.md`. Default cross-review:

```text
Claude implements → Codex reviews
Codex implements  → Claude reviews
```

The implementer may not independently approve its own work. See "## Multi-Agent Role Model" below for ownership, reviewer, shared-file, governance, and conflict rules.


### Independent auditor boundary

The independent auditor must not implement fixes during an audit unless implementation is separately and explicitly authorized.

The auditor must issue one of these verdicts:

```text
APPROVED
APPROVED WITH NON-BLOCKING NOTES
FIX REQUIRED
DESIGN REVISION REQUIRED
```

Developer handoff is evidence, not approval.

### Prompting rule

Implementation prompts to Claude should be intentionally concise.

They should include only:

- the authorized slice;
- the approved design/document to follow;
- critical invariants that must not be violated;
- explicit out-of-scope boundaries;
- concise handoff requirements.

Do not repeat large historical context or exhaustive audit/test checklists when that information already exists in repository documentation.

### Testing rule

Claude should:

- implement the authorized slice;
- add or adjust focused tests necessary for the implementation;
- reuse existing regression tests where possible;
- report exactly which tests were executed and their results.

The independent auditor is responsible for:

- checking whether test coverage is sufficient;
- identifying missing edge-case/evidence tests;
- validating claims against actual code/diffs;
- running or requesting additional verification when needed;
- distinguishing implementation defects from evidence gaps.

Do not make Claude generate broad additional tests solely to satisfy an audit checklist unless the independent auditor determines they are required to close a blocker.

### Default review-package policy

To reduce token usage without reducing audit quality:

- Full review packages are **not generated by default**.
- The default implementation handoff is concise and includes only:
  - files changed;
  - relevant diff or changed functions;
  - focused tests actually executed and their results;
  - known evidence gaps or deviations;
  - stop condition / current approval status.
- Generate a full `*_REVIEW_PACKAGE.md` only when:
  - explicitly requested by the independent auditor;
  - durable audit evidence is needed for a major milestone;
  - the auditor does not have direct repository access;
  - the working tree/branch state makes the relevant change difficult to inspect safely;
  - a handoff to another auditor requires a self-contained evidence package.
- For fix iterations, default to a short fix review:

```text
relevant old→new diff
+ focused regression test
+ actual result
+ remaining evidence gap
```

Do not embed complete source/test files in review artifacts unless specifically required.

### Test execution policy

During implementation/fix iterations:

- run focused tests for the changed behavior;
- reuse already-established regression evidence when still valid;
- do not repeatedly run broad unrelated suites.

Before final approval or handoff:

- run the relevant regression suite once;
- run a full system suite only when the scope/risk justifies it.

Never reduce evidence quality solely to save tokens.

PostgreSQL-specific behavior, external-provider behavior, concurrency, migration safety, and other high-risk claims still require the appropriate real evidence.

### Evidence rule

Never trade accuracy for token savings.

Agents must still report:

- tests actually run vs tests merely present;
- environment used;
- known failures;
- evidence gaps;
- PostgreSQL vs SQLite limitations where relevant;
- deviations from the approved design.

Concise prompts reduce duplication; repository documents preserve the full context.

## Multi-Agent Role Model

Claude and Codex may both act as developers; roles are assigned per authorized slice.
Every slice must identify:

```text
module / slice
primary implementer
independent reviewer
authorized scope
explicit out-of-scope boundaries
branch/worktree
known evidence requirements
```

The authoritative current assignment lives in `docs/03_CURRENT_WORK.md`. Default
cross-review: Claude implements → Codex reviews; Codex implements → Claude reviews.
The implementer may not independently approve its own work. The independent reviewer
must not implement fixes during the same audit unless ownership is separately and
explicitly transferred; if the reviewer returns `FIX REQUIRED`, the original
implementer performs the fix unless ownership is explicitly transferred. Allowed
verdicts: `APPROVED`, `APPROVED WITH NON-BLOCKING NOTES`, `FIX REQUIRED`,
`DESIGN REVISION REQUIRED`. Developer handoff is evidence, not approval.

### Domain Preferences

Unless `docs/03_CURRENT_WORK.md` assigns otherwise — these are preferences, not
authorization:

- Claude: Kitchen / KDS / Expo; core Order lifecycle; Payment/Security when separately authorized; broad cross-domain architecture when explicitly assigned.
- Codex: Schedule; Reservations; other self-contained modules explicitly assigned.

### Schedule / Reservations Boundary

When Codex is the authorized implementer for Schedule / Reservations, module-local
scope may include reservation/schedule services, routers, templates, module-specific
validation, focused unit/integration tests, overlap/availability behavior after
approved design, and module-local schema/index additions after explicit authorization.
Codex must stop and request scope expansion before redesigning or materially changing:
Order/OrderItem lifecycle; payment/deposit/refund behavior; table-open semantics
outside the approved reservation contract; BusinessDay/DayClose semantics; global
timezone; auth/authorization architecture; the shared migration framework; reporting
contracts; Kitchen/KDS behavior.

### Shared-File Rule

When an authorized slice touches a shared file: (1) identify the exact hunks belonging
to the slice; (2) avoid incidental cleanup/refactoring; (3) preserve unrelated
working-tree changes; (4) use partial staging or an isolated branch/worktree when
needed; (5) the reviewer validates the actual diff, not merely the final file. Common
shared files: `app/main.py`, `app/migrate.py`, `app/models/oltp.py`,
`web/templates/base.html`, `web/static/app.css`.

### Branch / Worktree Isolation

Parallel implementation should use separate branches/worktrees whenever practical. Do
not develop two unrelated slices in one dirty working tree when isolation is practical.
No agent may automatically merge, rebase, cherry-pick, reset, clean, push, resolve
integration conflicts, or alter Git history. Integration is a separate authorized
action.

### Developer Worktree Bootstrap

This applies equally to Claude and Codex whenever either is the implementer. Required
behavior **before** starting an authorized implementation slice:

1. Inspect the current state:

   ```text
   git status
   git branch --show-current
   git rev-parse --short HEAD
   ```

2. If the current working tree contains unrelated or dirty work, do **not** stash it,
   clean it, reset it, discard it, move it, or overwrite it.

3. Create an isolated branch/worktree from the **exact authorized base checkpoint**.

4. Naming convention:

   ```text
   branch:            feat/<slice-name>
   sibling worktree:  ../restaurant_<slice-name>
   ```

5. Verify **inside the new worktree**: correct branch; clean `git status`; correct base
   ancestry.

6. Perform all implementation for the slice **only** inside the isolated worktree.

7. Do not merge, rebase, cherry-pick, push, delete the worktree, or integrate the slice
   without explicit authorization.

8. At handoff, report: worktree path; branch; base checkpoint; files changed; tests
   executed + results; `git status --short`; evidence gaps.

9. If isolation cannot be created safely: **STOP and request a decision.**

### Approved Slice Commit Ownership

Applies equally to Claude and Codex. Required process:

1. The primary implementer completes the authorized slice.
2. The independent reviewer audits it.
3. If the verdict is `APPROVED` or `APPROVED WITH NON-BLOCKING NOTES`, the **primary
   implementer** may commit the approved slice.
4. The reviewer must **not** commit the implementer's work.
5. The implementer stages and commits **only**: files/hunks inside the approved scope,
   and the approved tests/evidence/docs belonging to that slice.
6. Before committing, verify the staged diff.
7. Commit does **not** authorize: merge; push; rebase; cherry-pick; integration;
   deployment; or cleanup/reset of unrelated work.
8. If the reviewer returns `FIX REQUIRED` or `DESIGN REVISION REQUIRED`: do not create
   the final approved-slice commit; the implementer performs the authorized
   fix/revision; independent review happens again before the final commit.
9. At commit handoff, report: commit SHA; `git log -1 --oneline`; `git status --short`;
   confirmation that only the approved scope was committed.

### Governance Check

A separate governance agent may be introduced later. Until one is explicitly assigned,
governance-agent automation is **not active** (Governance agent = NOT YET ASSIGNED;
GitHub/CI enforcement = NOT YET CONFIGURED). When assigned, it reports: authorized
scope respected; implementer != reviewer; shared-core change without authorization;
unrelated work mixed into slice; required evidence present; canonical docs consistent;
branch/worktree discipline respected — each YES/NO, a critical `NO` prevents clearance.
The governance agent may identify exceptions/conflicts but may not invent or approve
policy exceptions.

### Human Authority

The repository owner remains final authority for architecture exceptions, policy
changes, cross-domain scope expansion, unresolved Claude↔Codex disagreement, and
exceptional merge/deployment decisions. Agents must stop rather than invent an
exception.

### Technical Enforcement

GitHub Actions / CI / rulesets may later enforce deterministic policy (required tests,
lint/static checks, branch protections, required reviews, forbidden generated
artifacts, scope/path checks, migration checks). CI supplements but does not replace
independent review, semantic governance, or human authority. Do not claim these gates
are active until actually configured.

### Conflict Protocol

If Claude and Codex disagree: (1) neither silently overrides the other; (2) classify as
code defect, evidence gap, architecture decision, or authorization/scope issue;
(3) consult `docs/02_DECISIONS.md` and `docs/03_CURRENT_WORK.md`; (4) if unresolved,
stop implementation; (5) request explicit human decision. No agent may convert
disagreement into an implicit architecture decision.

### Ownership Transfer

Ownership may change between slices. A transfer must record in
`docs/03_CURRENT_WORK.md`: module/slice, previous implementer, new implementer,
reviewer, authorized scope, branch/worktree, known blockers/evidence gaps. Do not
create agent-specific permanent policy files for ownership transfer.

This role-model change is governance/process only. It does not reopen or authorize any
product feature, and does not weaken existing Kitchen invariants (closed B2 status),
Payment/Security approved-but-unmerged boundaries, SQLite-vs-PostgreSQL evidence rules,
concurrency discipline, financial/security safety, token-efficient handoff rules, Git
safety, or evidence vocabulary.

## Kitchen B2 Baseline

B2 v3 design, B2.1 and B2.2 are approved. The Kitchen B2 checkpoint was independently
re-audited at `f4dd079` — **APPROVED WITH NON-BLOCKING NOTES** — so Kitchen Stage B2 /
B2.2 are APPROVED / CLOSED. The contract below is the approved, committed behavior.

For task-backed fired work in task-mode KDS:

- PreparationTask is prep-state authority;
- station membership comes from snapshotted `PreparationTask.station_id`;
- one OrderItem remains one sale line;
- task READY is `PREPARING → READY` or idempotent `READY → READY`;
- unsupported task state is rejected;
- parent Order is the synchronization lock;
- state used for transition/rollup is refreshed/reselected after acquiring the lock;
- legacy writes on task-backed items route through tasks and validate all targets before mutation;
- coarse PREPARING resets all active stations and must be explicitly presented as destructive;
- tasks do not own SERVED;
- payment gate remains unchanged.

Task-mode activation requires:

```text
B2_2_ACTIVE
AND kitchen_b2_active
AND fired_items_without_tasks(db) == 0
```

A blocked activation serves the complete Stage A board, never a hybrid.

Real PostgreSQL concurrency evidence exists for the parent-Order lock/post-lock refresh contract.

B3/B4 and later cleanup remain separate, not implied by any B2 status.

## Payment / Financial Safety

Before changing payment/refund behavior inspect:

- current payment model;
- approved-but-unmerged Stage 1/2a/2b;
- transaction boundaries;
- provider side effects;
- idempotency;
- durable evidence;
- reporting/ETL;
- permissions;
- concurrency;
- migration impact.

Never assume:

```text
local Payment == processor truth
local Refund == processor refund
```

Current Floor/Kitchen risks include Square success before local commit, incomplete processor evidence, and local card Refund not executing Square reversal.

Do not implement ad hoc fixes that conflict with approved remediation architecture.

## Money Rules

Persist financial money in integer minor units.

Review subtotal, tax, tips, discounts, service charge, surcharge, balance, refunds, and reporting end-to-end when modifying money logic.

Do not casually recompute historical snapshots from mutable config.

## Authentication / Authorization

PINs use PBKDF2-HMAC-SHA256 with salt and legacy migration.

Do not regress to plaintext/weak hashing.

Backend authorization is authoritative.

Unknown/invalid permission cases should fail closed.

## Production Configuration

Treat current fail-open defaults as CURRENT RISK.

Approved Stage 1 establishes the fail-closed target but remains unmerged.

Never expose secrets in code/docs/logs/tests.

Do not change production environment values without explicit authorization.

## Database / Migration Discipline

Before schema change:

1. identify SQLite/PostgreSQL behavior;
2. inspect migration mechanism;
3. define additive compatibility;
4. define integrity invariant;
5. define backfill behavior;
6. define failure behavior;
7. define concurrency behavior;
8. define rollback/compatibility implications;
9. test;
10. record evidence limits.

SQLite is not PostgreSQL proof.

Do not silently change best-effort backfills into fatal migrations or vice versa.

## Concurrency Discipline

Sequential success is not concurrency proof.

Inspect transaction boundaries, row locks, stale ORM state, unique constraints, state guards, duplicate requests, multi-worker behavior, and two-terminal behavior.

High-risk paths: fire, task READY, SERVED, payment, refund, table open, reservations, closeout, migrations/backfills.

When locking a parent Order, refresh state used for decisions after lock acquisition.

## KDS Query Discipline

- filter before LIMIT;
- preserve deterministic ordering;
- avoid N+1;
- do not duplicate sale quantity;
- preserve inactive live-work access;
- preserve Unassigned;
- do not alter top-level status semantics incidentally.

## Performance Discipline

Distinguish:

```text
index exists
```

from:

```text
query plan confirms index use
```

Distinguish static hotspot analysis from measured performance.

No current load benchmark exists.

## Time / Reporting Discipline

Current model uses restaurant-local time and local calendar-date DayClose.

Changes to UTC/timezone/DST/closeout/reservation/reporting boundaries require explicit cross-domain analysis.

Reporting uses OLTP-to-star ETL.

## UX / Device Evidence Discipline

Responsive CSS does not prove device support.

Do not claim tablet, phone, touch, browser, or accessibility support without evidence.

Operational UX must preserve safe status and retry semantics, especially for money and Kitchen actions.

## Integration Discipline

For external providers identify source of truth, durable IDs, timeout, retry/idempotency, provider-success/local-failure behavior, and recovery/reconciliation.

Do not add integrations speculatively.

## Privacy / Auditability

Before logging/exporting data, consider guest/customer, staff, reservation, and payment metadata.

Application logs are not automatically durable audit logs.

Do not expose secrets or raw card data.

Do not claim PCI/legal compliance without separate evidence.

```text
TEST EXISTS
```

```text
TEST EXECUTED AND PASSED
```
